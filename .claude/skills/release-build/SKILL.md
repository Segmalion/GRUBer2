# release-build

Собирает Release-версии `GRUBer.exe` и `DeviceLister.exe`, раскладывает их в
`D:\UsersFiles\JOB-PROJECTS\TEST\GRUBer-RELEASE\[GRUBer_<версия>][DL_<версия>][<коммит>]\`,
подписывает оба файла сертификатом (thumbprint `B4D511E8418E0957521FE045EAAB39BA72B70F18`) и
упаковывает подписанные файлы в архив `[GRUBer_<версия>][DL_<версия>][<коммит>].7z` рядом с
этой папкой, в `D:\UsersFiles\JOB-PROJECTS\TEST\GRUBer-RELEASE\`.

После того как сборка+подпись+архивация прошли успешно, скилл убирает предыдущий релиз из
`GRUBer-RELEASE\`: старую папку релиза удаляет (её содержимое уже есть в новом архиве), а
старый `.7z`-архив переносит в `GRUBer-RELEASE\OLD_VERSION\`, не удаляя — так в основной папке
всегда лежит только актуальный релиз, а история архивов сохраняется.

Перед сборкой автоматически приводит git в порядок (коммитит и пушит без вопросов) — иначе
версия/коммит в имени папки и в `GitVersion.h` (см. `tools\gen_gitversion.bat`) не будут
отражать то, что реально попадёт в релиз.

## Шаги

### 0. Версия (спросить)

Перед коммитом спросить пользователя (`AskUserQuestion`), нужно ли менять версию GRUBer
и/или DeviceLister перед сборкой этого релиза.

- **Нет** — версию не трогаем, переходить к шагу 1 как есть.
- **Да** — вызвать скилл `/version-update` (через `Skill`) и дождаться его завершения. Он сам
  по отдельности спросит про GRUBer и про DeviceLister (оставить как есть / +1 к Build /
  ввести вручную) и поправит нужные `VerInfo_*`/`FileVersion` поля в соответствующих
  `.cbproj`. После его завершения продолжить с шага 1 — изменённые `.cbproj` подхватятся тем
  же коммитом, что и остальные незакоммиченные изменения.

### 1. Коммит (автоматически, без вопросов)

Выполнить `git status --porcelain` в корне репозитория.

- Если вывод пустой — рабочее дерево чистое, перейти к шагу 2.
- Если есть незакоммиченные изменения — застейджить релевантные файлы (не слепой `git add -A`;
  изучить `git status`/`git diff`, исключить мусор и файлы с потенциальными секретами по
  общему git-протоколу), сгенерировать краткое сообщение коммита по содержимому диффа и
  закоммитить с атрибуцией Claude из системного промпта этой сессии — без подтверждения у
  пользователя.

### 2. Пуш (автоматически, без вопросов)

Выполнить `git fetch` (только чтение), затем проверить, сколько локальных коммитов впереди
апстрима: `git rev-list @{u}..HEAD --count`. Если апстрим не настроен — считать это как "не
запушено".

- Если коммитов впереди 0 — перейти к шагу 3.
- Если >0 (или апстрима нет) — сразу `git push` (на текущую ветку/апстрим; если апстрима нет —
  `git push -u origin <текущая ветка>`), без подтверждения у пользователя.

### 3. Сборка и подпись

Запустить (через PowerShell-инструмент, не Bash — скрипт вызывает `rsvars.bat`/`msbuild`,
которые нужны в реальном Windows-окружении):

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_release.ps1 -Config Release
```

Это выполнит: `msbuild GRUBer2.groupproj /t:Build /p:Config=Release /p:Platform=Win64x`,
считает фактическую версию из собранных `GRUBer.exe`/`DeviceLister.exe`
(`VersionInfo.FileVersion`), создаст папку релиза, скопирует оба exe, подпишет их
`signtool.exe`, упакует подписанные файлы в `.7z`-архив рядом с папкой релиза (7-Zip берётся
из `C:\Program Files\7-Zip-Zstandard\7z.exe`) и только после этого удалит предыдущую(-ие)
папку(-и) релиза в `GRUBer-RELEASE\`, а предыдущий(-ие) архив(-ы) `.7z` перенесёт в
`GRUBer-RELEASE\OLD_VERSION\`.

Стримить вывод пользователю по ходу выполнения. Если скрипт упал (билд, отсутствующий
сертификат, ошибка signtool или 7z) — показать ошибку как есть, **не** докладывать об успешном
релизе и не переходить к шагу 4.

### 3.5. Публикация релиза на GitHub (опционально)

После успешной сборки+подписи+архивации спросить пользователя (`AskUserQuestion`) ОДНИМ
вопросом — публиковать ли эту сборку как GitHub Release в `Segmalion/GRUBer2` (приватный
репозиторий) — это то, что GRUBer.exe умеет находить и скачивать через встроенную автопроверку
обновлений (`Th_UpdateCheck`/`UpdateCheck.cpp` в `src_grub`). Публикация — не обязательна,
локальная сборка без неё остаётся полностью рабочим сценарием. **Ничего про release notes на
этом шаге не спрашивать** — вопрос про notes идёт отдельным шагом и только если выбрали
"Опубликовать" (см. ниже); задавать его раньше вопроса о публикации не нужно, чтобы не
спрашивать пользователя о том, что может вообще не понадобиться.

- **Не публиковать** — просто собрать локально, как раньше. Дальше по этому шагу ничего не
  делать (release notes не готовим, `-Notes` не собираем) — сразу переходить к шагу 4.
- **Опубликовать** — только теперь подготовить текст release notes:
  1. Найти последний опубликованный релиз: `gh release list --repo Segmalion/GRUBer2 --limit 1`
     (тег — короткий commit hash). Если релизов ещё нет — взять весь `git log` текущей ветки.
  2. Собрать черновик по коммитам с того тега до `HEAD`: `git log <тег>..HEAD --oneline`
     (или `--format=%s` без хешей) — и сжать в 2–5 пунктов на человеческом языке (не список
     commit-сообщений as-is, а краткое осмысленное описание того, что изменилось для
     пользователя — багфиксы, новое поведение и т.п.).
  3. Показать черновик пользователю через `AskUserQuestion` (текст черновика — в самом
     вопросе) и спросить, использовать ли его как есть, отредактировать (свободный ввод через
     "Other"), или оставить notes пустыми (тогда `-Notes` не передавать — скрипт сам
     подставит заголовок релиза вместо notes, прежнее поведение).
  4. Повторно вызвать (или изначально вызвать) сборку с флагами `-Publish` и `-Notes`:
     ```
     powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_release.ps1 -Config Release -Publish -Notes "<текст>"
     ```
     Скрипт тегирует релиз коротким хешем коммита (тем же, что `GIT_COMMIT_HASH` в собранном
     exe), прикладывает **только оба подписанных exe** (`GRUBer.exe`, `DeviceLister.exe`) как
     ассеты — `.7z`-архив в релиз не грузится, он остаётся только локально в
     `GRUBer-RELEASE\` (автопроверка обновлений ищет ассеты именно по этим двум именам
     файлов, архив ей не нужен) — и печатает ссылку на опубликованный релиз.

`-Notes` попадает в GitHub Release body (`rel.body`), который GRUBer.exe показывает в диалоге
"Доступне оновлення" (`Th_UpdateCheck.cpp`) под заголовком "Що нового" — так пользователи на
местах видят, что реально изменилось, а не только номер версии.

Публикация возможна только если дерево чистое и запушено (шаги 1–2 это уже гарантируют) —
"грязная" (`-dirty`) сборка никогда не публикуется, иначе её тег не совпадёт ни у кого с
`GIT_COMMIT_HASH`.

Предпосылка: переменная окружения `GRUBER_RELEASE_TOKEN` с GitHub-токеном, у которого есть
права на публикацию релизов в этом репозитории (fine-grained PAT, `Contents: Read and write`,
только `Segmalion/GRUBer2`). Это **отдельный** токен от read-only токена, зашитого в
`GRUBer.exe` (`src_grub/UpdateSecrets.h`, гитигнорится) — этот, write-scoped, живёт только на
машине разработчика и никогда не попадает в код программы. Публикация использует `gh` CLI,
если он установлен (подхватывает токен через `GH_TOKEN`), иначе — прямые вызовы GitHub REST
API через `Invoke-RestMethod`.

### 4. Итог

Сообщить пользователю финальный путь к папке релиза, архиву и список подписанных файлов,
например:

```
Готово: D:\UsersFiles\JOB-PROJECTS\TEST\GRUBer-RELEASE\[GRUBer_0.3.5.4][DL_0.0.2.2][a1b2c3d]\
  - GRUBer.exe (подписан)
  - DeviceLister.exe (подписан)
Архив: D:\UsersFiles\JOB-PROJECTS\TEST\GRUBer-RELEASE\[GRUBer_0.3.5.4][DL_0.0.2.2][a1b2c3d].7z
```

## Предпосылки

Предпосылки для машины, на которой запускается сборка:
- Установлена RAD Studio 37.0 (используется `rsvars.bat` из
  `C:\Program Files (x86)\Embarcadero\Studio\37.0\bin\`).
- В хранилище сертификатов Windows есть сертификат с thumbprint
  `B4D511E8418E0957521FE045EAAB39BA72B70F18`, и доступен
  `C:\Program Files (x86)\Microsoft SDKs\ClickOnce\SignTool\signtool.exe`.
- Есть сетевой доступ к `http://timestamp.digicert.com` (сервер штампа времени для подписи).
- Установлен 7-Zip (сборка Zstandard) по пути
  `C:\Program Files\7-Zip-Zstandard\7z.exe`.
- Для шага 3.5 (публикация, только если её выбрали): установлен `gh` CLI **или** доступен
  PowerShell 5.1+ для REST-фолбэка, и в окружении задан `GRUBER_RELEASE_TOKEN`
  (write-scoped GitHub PAT на `Segmalion/GRUBer2`).

Если что-то из этого изменится (новая версия RAD Studio, другой сертификат, другой путь к
TEST-папке) — поправьте константы в начале `tools\build_release.ps1`.
