# version-update

Меняет версию (`Major.Minor.Release.Build`, например `3.6.0.0`) у **GRUBer** и/или
**DeviceLister** — независимо друг от друга, каждый со своим текущим значением и своим
решением пользователя. Версия хранится в `VerInfo_MajorVer`/`VerInfo_MinorVer`/
`VerInfo_Release`/`VerInfo_Build` и продублирована в `FileVersion=...` внутри `VerInfo_Keys` —
см. `CLAUDE.md` ("Versioning — commit-traceable version string"). Это ручной номер релиза,
отдельный от автоматического `GIT_COMMIT_HASH`/`GitVersion.h` — этот скилл `GitVersion.h` не
трогает (он генерируется сам при сборке).

## Почему это не тривиальная правка одной строки

В `.cbproj` версия задаётся в нескольких `PropertyGroup`, потому что MSBuild-проект
Embarcadero хранит настройки отдельно на Base/Debug(`Cfg_1`)/Release(`Cfg_2`) и отдельно на
Win32/Win64/Win64x — даже для платформ, которые уже не собираются (`Win32` — инертный мусор,
см. `CLAUDE.md`). У **GRUBer.cbproj** реальную версию несут три блока: `Base`, `Cfg_2_Win32`
(инертный, но исторически держится в синхроне) и `Cfg_2_Win64x` — у всех трёх одинаковые
значения. У **DeviceLister.cbproj** структура кривее: `VerInfo_MajorVer`/`Release`/`Build` и
`FileVersion` реально обновлялись только в блоке `Cfg_2_Win64x`, а более общий блок `Cfg_2`
(без платформы) остался с устаревшими цифрами ещё с версии `0.0.1.2` — это не баг, который
нужно чинить попутно, а исторический факт; не удивляться и не "исправлять" его молча, если
пользователь не просил.

Реальная версия, которая попадёт в собранный `.exe` (Release/Win64x — единственная
собираемая конфигурация), всегда берётся из блока с условием, содержащим `Cfg_2_Win64x`.
Именно этот блок — источник истины для "текущей версии", которую нужно показать пользователю.

## Шаги

### 1. Прочитать текущую версию каждого проекта

Для `src_grub\GRUBer.cbproj` и `src_devLister\DeviceLister.cbproj` по отдельности:

```
grep -n -A 15 "Cfg_2_Win64x'!=''\"" <файл.cbproj>
```

В выведенном блоке найти `FileVersion=X.X.X.X` внутри `VerInfo_Keys` — это и есть текущая
версия проекта (`Major.Minor.Release.Build`). Сохранить её отдельно для GRUBer и для
DeviceLister — дальше с каждым проектом работаем независимо.

### 2. GRUBer — уточнить у пользователя

Показать текущую версию GRUBer и спросить (`AskUserQuestion`), что делать:

- **Оставить как есть** — версию не трогаем, к DeviceLister переходим без изменений в файле.
- **Увеличить на +1** — увеличивает **последнюю цифру (Build)** на 1, остальные три —
  без изменений (например `3.6.0.0` → `3.6.0.1`). Именно так исторически бампались обе
  программы (см. `git log`: `0.3.5.3 → 0.3.5.4`, `0.0.2.1 → 0.0.2.2` — всегда только Build).
- **Ввести вручную** — после выбора этого варианта задать в чате обычным текстом вопрос
  "Какую версию установить для GRUBer? (Major.Minor.Release.Build)" и дождаться ответа.
  Провалидировать, что это ровно 4 неотрицательных целых числа через точку.

Если выбрано "оставить как есть" — файл не редактируется, переходить к шагу 4 (DeviceLister).

### 3. GRUBer — применить новую версию

Дана новая версия `NEW = Major.Minor.Release.Build`. В `src_grub\GRUBer.cbproj`:

1. `grep -n "VerInfo_MajorVer\|VerInfo_MinorVer\|VerInfo_Release\|VerInfo_Build\|FileVersion="`
   по файлу — получить список всех строк с текущими значениями (в трёх блоках: `Base`,
   `Cfg_2_Win32`, `Cfg_2_Win64x`).
2. Для каждой найденной строки — точечный `Edit` (не `replace_all` вслепую, если в разных
   блоках разные текущие числа — правьте с достаточным контекстом строки, чтобы old_string
   был уникален):
   - `<VerInfo_MajorVer>N</VerInfo_MajorVer>` → новый Major (обычно только в `Base`)
   - `<VerInfo_MinorVer>N</VerInfo_MinorVer>` → новый Minor (обычно только в `Base`)
   - `<VerInfo_Release>N</VerInfo_Release>` → новый Release (во всех трёх блоках)
   - `<VerInfo_Build>N</VerInfo_Build>` → новый Build (во всех трёх блоках)
   - внутри каждого `VerInfo_Keys>...FileVersion=X.X.X.X;...` — заменить именно
     `FileVersion=X.X.X.X` на `FileVersion=NEW`. **Не трогать** соседний `ProductVersion=...`
     в той же строке — это отдельное, не связанное с версией приложения поле, его менять не
     нужно.
3. `grep -n "FileVersion=" src_grub\GRUBer.cbproj` ещё раз — все три вхождения должны
   показывать одинаковый `NEW`.

### 4. DeviceLister — уточнить у пользователя

Аналогично шагу 2, но для DeviceLister и его текущей версии (обычно только блок
`Cfg_2_Win64x` несёт актуальные цифры — см. секцию выше про кривую структуру). Те же три
варианта: оставить как есть / +1 к Build / ввести вручную.

### 5. DeviceLister — применить новую версию

Дана новая версия `NEW`. В `src_devLister\DeviceLister.cbproj`:

1. `grep -n "VerInfo_MajorVer\|VerInfo_MinorVer\|VerInfo_Release\|VerInfo_Build\|FileVersion="`
   по файлу.
2. Обновить теги **только в блоке `Cfg_2_Win64x`** (условие содержит `'$(Cfg_2_Win64x)'!=''`)
   — это единственный блок, который реально влияет на собранный `.exe`, и единственный,
   который исторически обновлялся. Блоки `Base` (`FileVersion=1.0.0.0`) и `Cfg_2` без
   платформы (устаревшие `MajorVer=0`/`Release=1`/`Build=2`/`FileVersion=0.0.1.2`) **не
   трогать**, если пользователь явно не попросил их тоже привести в порядок — это осознанный
   исторический беспорядок в проекте, а не то, что вписывается в задачу "смени версию".
   - Если новый Major/Minor отличается от текущего, а тега `VerInfo_MajorVer`/
     `VerInfo_MinorVer` в блоке `Cfg_2_Win64x` нет (сейчас там их нет вообще — Major
     наследуется из блока `Cfg_2`, Minor нигде не задан и равен 0 по умолчанию) — добавить
     туда `<VerInfo_MajorVer>N</VerInfo_MajorVer>` / `<VerInfo_MinorVer>N</VerInfo_MinorVer>`
     рядом с `VerInfo_Build`/`VerInfo_Release`, а не редактировать блок `Cfg_2`. Такое нужно
     только при ручном вводе версии с другим Major/Minor — при "оставить как есть" и "+1" оба
     всегда остаются `0`, так что это не понадобится.
3. `grep -n "Cfg_2_Win64x'!=''\"" -A 15 src_devLister\DeviceLister.cbproj` ещё раз — убедиться,
   что `FileVersion=NEW` и все VerInfo_* внутри этого блока согласованы.

Коммит, пуш и сборка/релиз в этот скилл не входят — это отдельные шаги (обычный git-коммит
вручную или `/release-build`), если они понадобятся.

## Как пользоваться

Вызов: `/version-update` в сессии Claude Code внутри репозитория GRUBer2, либо просьба
"смени версию" / "обнови версию".

Что произойдёт:
1. Скилл покажет текущую версию GRUBer и спросит: оставить как есть / +1 к Build / ввести
   вручную.
2. Применит выбор (если не "оставить как есть") ко всем актуальным `VerInfo_*`/`FileVersion`
   местам в `GRUBer.cbproj`.
3. Затем то же самое отдельно для DeviceLister (со своей текущей версией и своим выбором).

Ничего не коммитится, не собирается, не пушится и не публикуется — только правка версии в
исходниках проекта.
